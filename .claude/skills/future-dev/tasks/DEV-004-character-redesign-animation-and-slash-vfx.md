### Objective
The combat characters currently animate from a tiny 5-frame sheet, so movement reads
stiff. Redesign the ninja figure at a larger native resolution with a much richer
animation set (fluid run, jump arc, dash, throw, katana attack, guard, hurt, death),
keep the katana as a separately-generated sprite that anchors to the hand, and add a new
**film-style katana slash-trail VFX** (a fast blade leaving an elongated motion-blur
smear/arc, anime "iaido flash" look). Deliver this as: (A) a precise art-generation spec
the user can paste into a Claude chat, and (B) the engine integration that consumes the
new sheets.

### Context — the CURRENT sprite system (account for this exactly)
- **Native size:** 16×16 px per frame, drawn **facing LEFT** (the game mirrors via
  `flip_h`/negative scale when facing right — see `player.gd` ≈ 1553).
- **Pose sheet:** `80×16` = **5 frames**, fixed order `idle, walk1, walk2, jump, attack`.
  Defined in `ninja_clash/sprites/ninjas/generate_ninjas.py` (`POSES`, line 12) and must
  match `player.gd` consts (≈ 78-83): `FRAME_IDLE/WALK_1/WALK_2/JUMP/ATTACK`.
- **Idle sheet (base skin only):** `96×16` = **6 frames**
  (neutral/inhale/exhale/blink/look-L/look-R), played by `IDLE_PATTERN` (`player.gd`
  ≈ 192). The other 7 styles have NO idle sheet → they fall back to a single static idle
  pose. This is a big part of "too few frames."
- **Skins:** 8 styles × 4 clan colors = **32 skins**.
  - Styles: `base, elemental, chef, cyber, edo, office, pirate, vacation`
    (`game_state.gd:41` `SKIN_STYLES`).
  - Clan colors: `cyan, magenta, orange, green`, each a 3-shade palette (main/hi/shadow,
    `generate_ninjas.py:19` `PALETTES`).
  - Elemental names per color: magenta→wraith, cyan→tempest, green→glacier,
    orange→inferno (`game_state.gd:43`).
  - Each skin ships **native + 4x + 8x** PNGs (e.g. `_native_80x16`, `_4x_320x64`,
    `_8x_640x128`), transparent bg, nearest-neighbor import.
- **Path resolution:** `GameState.skin_pose_path(color, style_idx)` and
  `skin_idle_path(...)` (`game_state.gd` ≈ 94-106) build the filenames; the menus
  (`clan_select.gd` `_ninja_atlas`, ≈ 150) read frame 0 as a `16×16` AtlasTexture region.
- **Animation selection:** `player.gd._update_visual()` (≈ 1500) is a hand-rolled state
  picker that just sets `visual.frame` to one of the 5 indices: defending→idle frame,
  sliding/throwing→attack frame, airborne/wall-grab→single jump frame, moving→alternate
  walk1/walk2, idle→6-frame breathing (base) or static idle. Run = 2 frames; jump/fall/
  land = 1 frame; throw/attack = 1 body frame; no dash/wall-slide/hurt/death frames.
- **Katana is SEPARATE** from the body: a `Sprite2D` child named `Katana` using a 6-frame
  "V2" sheet (`sheathed, drawn, raised, mid_swing, strike_hit, follow_thru`). The body
  only shows the ATTACK frame during a swing; the blade sprite is positioned by anchoring
  a **grip pixel** to the hand via `Sprite2D.offset` with hardcoded per-frame offsets
  (`player.gd` ≈ 1563-1587). Keep this decoupled approach.
- **Existing FX-sheet pattern (model for the new slash VFX):** `fx_anim.gd` plays frame
  strips like `sprites/fx/clash_lightning_5frame_native_160x32.png` (5 frames) and
  `sprites/fx/strike_flash_4frame_native_96x24.png` (4 frames), spawned from helpers in
  `player.gd` (≈ 1197 clash spark, ≈ 1212 strike flash). The new katana slash trail is
  the same kind of asset on this same pipeline.

### Decisions already made (by the user)
- **Native size:** move UP from 16×16 to a larger canvas — **recommend 32×32** (24×24
  acceptable). Pick one and apply it consistently to ALL 32 skins.
- **Visual:** **fresh redesign** of the ninja look (not just reskinned current art),
  while keeping each of the 8 style identities (chef/cyber/edo/office/pirate/vacation/
  elemental/base) recognizable and the 4 clan palettes intact.
- **Katana:** keep it as a **separately-generated** sprite (not baked into the body).
- **New asset:** a **katana slash-trail VFX** — a fast blade leaving a stretched,
  film/anime motion-blur smear that elongates along the swing arc then thins and fades.

### Deliverable A — Redesigned ninja figure + animation set (generation spec)
Produce, for EACH of the 32 skins (8 styles × 4 clan colors):

- **Frame size:** 32×32 px (or chosen size), facing LEFT, transparent background,
  pixel-art with the per-clan 3-shade palette; consistent silhouette and a **documented
  foot-anchor baseline row** (the pixel row the feet rest on) so the engine can place the
  larger sprite on platforms without floating/sinking.
- **Sheet layout:** a single sheet with a documented frame grid (left→right, optional
  rows), plus a **machine-readable animation map** (JSON or GDScript table) listing each
  animation's `start_frame`, `frame_count`, `fps`, and `loop` flag. This map is the
  contract the engine integration reads.
- **Recommended animation set** (tune counts during generation; these are minimums for
  "fluid"):
  - `idle` — 4-6 frames (breathing + blink), for ALL skins now (not just base).
  - `run` — 6-8 frames (full cycle; replaces the 2-frame walk).
  - `jump_up` 2 · `apex` 1 · `fall` 2 · `land` 2 (a real jump arc instead of one frame).
  - `crouch` — 1-2 frames (low ducked stance + a brief settle). The game has NO crouch
    state today; treat this as a VISUAL pose bound to holding down (`aim_down`) while
    grounded and not moving — do not add new crouch-movement mechanics (see Assumptions).
    Also reusable as the `land` recovery / slide ground pose.
  - `dash`/`dodge` — 2-3 frames: a streaked, leaned-in tuck for the directional burst
    (lead-in → committed streak → recover). This is the BODY pose for the dash; it binds
    to the existing `is_sliding` state (the L2/R2 directional dodge, 8-way). Keep it
    distinct from the new slash VFX — the dash itself may also warrant a faint body
    motion-streak, but that is optional and separate from Deliverable C.
  - `wall_slide` — 1-2 frames (currently reuses the jump frame).
  - `throw` — 3 frames (windup → release → recover).
  - `katana_attack` (body) — 3 frames (windup → strike → recover), timed to sync with the
    separate katana sprite's swing.
  - `guard`/`block` — 1-2 frames (planted brace; currently reuses idle).
  - `hurt` — 1-2 frames; `death`/`collapse` — 2-3 frames (currently a rotated jump frame).
- **Exports & naming:** native + 4x + 8x per skin, nearest-neighbor, transparent.
  Define the new filename scheme (the old `_native_80x16` dimension suffix changes) and
  keep it derivable from `(style, color)` so `GameState.skin_pose_path/idle_path` can be
  updated mechanically.

### Deliverable B — Katana sprite (separate, regenerated to match)
- Regenerate the katana at the new resolution/style to match the redesigned ninja, as a
  standalone `Sprite2D` sheet. Provide at least `windup(raised)` and `strike(follow-thru)`
  frames; ideally the full 6-pose V2 set (sheathed/drawn/raised/mid_swing/strike_hit/
  follow_thru).
- **Critical:** document the **grip-pixel coordinate (x,y) per frame** so the engine can
  anchor the handle to the hand via `Sprite2D.offset` (the current hardcoded offsets in
  `player.gd` ≈ 1569-1587 must be recomputed for the new art). Keep the blade drawn
  blade-LEFT so the existing negative-scale mirror logic still works.

### Deliverable C — Katana slash-trail VFX (the film-style smear)
- A short animated **slash arc**: the blade's path leaves a bright thin leading core with
  a translucent, elongated motion-blur trail that **stretches** along the swing arc at
  peak, then thins and fades — anime/film "fast blade" look.
- **Format:** a frame strip consumed by the existing `fx_anim.gd` pipeline (like the
  clash/strike sheets). Recommend ~5-8 frames: arc forms → peak stretch (full elongated
  crescent + soft trail) → smear thins → fade-out.
- **Constraints:** transparent bg; oriented so the game can rotate/flip it to the swing
  direction; sized to roughly cover the swing reach (`KATANA_RANGE` ≈ 30 px,
  `katana_half_h` ≈ 18 px — see `player_tuning.gd`); **color-tintable** (white core,
  tintable to the clan color via `modulate`). Native + 4x/8x; place in
  `ninja_clash/sprites/fx/`. A soft-alpha trail is fine but keep it visually consistent
  with the pixel-art style.

### Deliverable D — Movement dust / "around-the-character" VFX (TowerFall-style juice)
Secondary effects spawned AROUND the fighter to add dynamism, in the TowerFall idiom:
- **Run dust** — small dust puffs/kick-up trailing behind the feet while running on the
  ground, emitted on a cadence (e.g. every other run-cycle footfall), drifting back and
  fading.
- **Jump dust** — a kick-off puff at the feet the moment a jump launches from the floor.
- **Land dust** — a wider impact puff when touching down from a fall (scale it a touch
  with landing speed for weightier landings).
- Consider also: wall-jump kick puff, and dash/slide scuff dust (reuse the run-dust look).
- **Format:** small frame-strip puff sheets on the existing `fx_anim.gd` pipeline (same as
  the clash/strike/slash sheets) — recommend ~4-5 frames each (puff appears → expands →
  thins → fades), transparent bg, neutral light-grey/dust tint that can be `modulate`-
  tinted per level if wanted. Native + 4x/8x, placed in `ninja_clash/sprites/fx/`.
  (A `GPUParticles2D`/`CPUParticles2D` emitter is an acceptable alternative for the
  continuous run trail, but keep it cheap and pixel-consistent; default to frame strips.)
- Spawn at the foot anchor, behind the character (z below the body), mirrored/offset by
  facing so dust trails *behind* the run direction.

### Generator scripts (.py) — one per situation, thoroughly documented (REQUIRED)
The project generates its pixel art procedurally with Python (Pillow), e.g.
`ninja_clash/sprites/ninjas/generate_ninjas.py` (palette dicts, per-pose draw functions,
native + 4x + 8x export) and `generate_level.py`. "Generated in a Claude chat" means
**writing/using these generator scripts** — so every generation situation above MUST ship
its own dedicated, well-documented `.py` generator (do not hand-place pixels ad hoc):

- One generator per asset family: **(A)** ninja figure + full animation set,
  **(B)** katana sprite, **(C)** katana slash-trail VFX, **(D)** each movement-dust puff.
  Split further per distinct situation if a single script gets unwieldy (e.g. a
  `generate_dust_run.py` / `generate_dust_jump.py` / `generate_dust_land.py`).
- Each script must, following the `generate_ninjas.py` convention:
  - Declare the **frame size, frame grid, and animation map** (start/count/fps/loop) as
    data at the top, and the **palette(s)** (per-clan main/hi/shadow for the ninja; tint
    for VFX) — no magic numbers buried in draw calls.
  - Provide one **draw function per pose/frame/situation**, composed from shared helpers
    (head/torso/limbs for the ninja; arc/trail builders for VFX) so frames stay coherent.
  - **Export native + 4x + 8x** (nearest-neighbor upscale, transparent bg) with the exact
    filenames `GameState`/the loaders expect, deterministically (same input → same output).
  - Be **runnable standalone** (`python generate_<thing>.py`) and emit into the correct
    `sprites/...` folder; document at the top: purpose, inputs, outputs (filenames), and
    the run command.
- A thorough header comment in each script documents what situation it covers, the frame
  layout, and how it maps to the in-engine animation/VFX it feeds. Keep the scripts in the
  repo so the art is reproducible and regenerable when the design changes.

### Engine integration requirements (make the generated art actually play)
1. **Animation driver:** replace the fixed `FRAME_*` index picking in
   `player.gd._update_visual()` with a real animation system that reads the animation map
   from Deliverable A — either migrate the body `Visual` to an `AnimatedSprite2D` +
   `SpriteFrames` resource, or an AtlasTexture/animation-table driver. Each gameplay state
   (idle/run/jump_up/apex/fall/land/crouch/dash/wall_slide/throw/katana_attack/guard/
   hurt/death) maps to a named animation; transitions driven by the existing state
   signals (`is_sliding` → dash, holding `aim_down` grounded+still → crouch,
   `throw_anim_until`, `is_on_floor`, `velocity`, `is_defending`, `is_swinging`, `alive`,
   etc.). The `crouch` binding is the only new visual state to wire — keep it purely
   cosmetic (no movement/hitbox change).
2. **Larger sprite vs hitbox:** keep the gameplay hitbox tuned — decouple the visual frame
   size from collision. If `PLAYER_W/PLAYER_H` or the visual scale must change, document
   it and re-verify collision, the platform foot-anchor, wall-grab contact, and stomp
   detection. Default stance: bigger *visual*, unchanged *hitbox*, unless intentionally
   rebalanced.
3. **Path + generator updates:** update `GameState.skin_pose_path` / `skin_idle_path`
   (`game_state.gd`) and the generator script(s)
   (`sprites/ninjas/generate_ninjas.py`, and the costume generator) for the new dimensions,
   frame counts, and filenames. Keep all 32 skins resolvable.
4. **Menu previews:** update every place that reads a `16×16` region — `clan_select.gd`
   `_ninja_atlas`/`NINJA_SIZE`, and any skin preview/HUD avatar — to the new frame size so
   menus don't crop/scale wrong.
5. **Katana anchor:** recompute the per-frame `offset` grip anchors in `player.gd` from
   Deliverable B's documented grip pixels; verify the blade grips the hand across windup
   and strike, and in the guard stance.
6. **Slash VFX hookup:** spawn Deliverable C's trail via `fx_anim` at the katana swing
   (alongside/!replacing the existing strike flash where appropriate), oriented to facing
   and positioned at blade reach in front of the fighter; tint to clan color.
7. **Movement dust hookup:** spawn Deliverable D's dust at the foot anchor (behind the
   body, z below it): run dust on a run-cycle cadence while grounded and moving, jump dust
   on floor jump-launch, land dust on touchdown from a fall (scale with landing speed),
   and optionally wall-jump/dash scuff. Drive it off the same state signals as the
   animation driver; keep emission cheap (pool/limit instances) within the frame budget.
8. **Import:** generate/verify `.import` files (nearest filter) for all new PNGs.
9. **Generators in-repo:** the `.py` generator scripts (above) are committed and runnable;
   re-running them reproduces every sheet the engine loads.

### Constraints
- Godot 4.6 / GDScript (see `docs/engine-reference/godot/VERSION.md`); training data
  predates 4.4–4.6 — cross-check `AnimatedSprite2D`/`SpriteFrames`/import APIs there.
- Follow CLAUDE.md: ask before writing files, keep data-driven (the animation map and
  palettes are data, not magic numbers), match conventions in `ninja_clash/`.
- Consistency across all 32 skins is mandatory: identical frame grid, anchor, facing, and
  animation map per skin; only the look/palette differs.
- 2D pixel-art game, 60 fps, <200 draw calls, <1 GB RAM (technical-preferences.md) — keep
  sheet sizes reasonable; the 8x exports are for menus/promo, gameplay uses native.
- VERIFY visually (coding-standards.md): screenshots of menus AND in-fight for several
  skins; confirm run/jump/dash/throw/attack read fluidly and the slash trail aligns to the
  blade; run the headless import/parse check (`reference_godot_headless_verify`).

### Assumptions
- Native frame size = 32×32 (switch to 24×24 if the user prefers tighter density); the
  gameplay hitbox stays as-is unless explicitly rebalanced.
- The katana stays a separate hand-anchored sprite (not baked into the body frames).
- The slash-trail VFX rides the existing `fx_anim` frame-strip pipeline, tintable per clan.
- "Generated in a Claude chat" = this task delivers the SPEC + integration; the actual
  pixel art is produced by the user externally and dropped into `sprites/`.
- `crouch` is a NEW visual-only pose bound to holding down (`aim_down`) while grounded and
  still; it adds no crouch-walk / fast-fall / hitbox-shrink mechanic (that would be a
  separate gameplay task). `dash` reuses the existing `is_sliding` dodge state — no new
  mechanic, just a dedicated body animation for it.
